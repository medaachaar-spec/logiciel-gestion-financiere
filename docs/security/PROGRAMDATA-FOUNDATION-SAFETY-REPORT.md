# ProgramData / Foundation safety investigation

## Result and scope

**FINAL RESULT: PASS — SAFE TO CONTINUE** for the scoped Foundation/ProgramData safety fix. Leave the Login feature and this work uncommitted for Lead review; this does not constitute manual UI release acceptance.

1. **Starting branch / SHA:** `feature/login-password-visibility-v1` / `b062f4dc7d8d8dd5639b7a35b1480ccc133da283`.
2. **Exact root cause:** The Desktop test host instantiated the *production* `App`, initialized its WPF resources, and started a dispatcher. WPF also dispatched its application Startup callback, entering `App.OnStartup`, which resolved `CommonApplicationData` to `C:\ProgramData\FinancialManagement\Data\FinancialManagement.db` and invoked production database initialization. Not calling `Application.Run` did **not** prevent this queued Startup callback.
3. **Root-cause evidence:** The former test host used `new FinancialManagement.Desktop.App()` followed by `Dispatcher.Run()` (`tests/FinancialManagement.Desktop.Tests/WpfTestHost.cs`, now lines 36–43). `App.OnStartup` obtains `ApplicationPaths` and calls `MigrateDatabaseAsync` (`src/FinancialManagement.Desktop/App.xaml.cs`, now lines 37–60); the path is assembled in `Configuration/ApplicationPaths.cs` lines 7–25. A new regression test observes `StartupCallbackObserved == true` on the WPF test dispatcher and confirms production mode is disabled. The before/after main DB images differ at only **12 bytes** on SQLite page 2: the old and new strings `2026-09-11 23:32:22.6237794+00:00` and `2026-09-12 00:22:26.4751583+00:00`, respectively, in free/deleted `__EFMigrationsLock.Timestamp` payload. This is consistent with repeated startup migration-lock activity. All visible tables, rows, `sqlite_sequence`, and schema have identical canonical logical SHA-256 `E8176FFC9457A33E1017F671D530F9C2913C720B871AD17E79AE625521B599E3` in the old and current filesystem copies. The main file's physical SHA-256 nonetheless changed from `562DAB1BC5FCD3A454E2C3490A1932DE370C1AE8051E463F08E5BFB59ABADACB` to `AAF447095C69BFE83E7DAB2944A4774B7711A31F45A0A6CEA94AC6D95617642A`.
4. **Process:** The exact historical PID was **not captured**. The responsible execution path is the Desktop `testhost.exe` WPF dispatcher, inferred from code, the demonstrated callback, and production SQLite lock residue. The earlier Procmon capture lacked its intended Path Include filter and is not used as proof. A new reliable filtered Procmon capture was not possible because its elevated window was unavailable to the native-control surface. Do not claim a measured PID.
5. **Responsible command/test/path:** `dotnet test FinancialManagement.sln` runs Desktop tests using `WpfTestHost.Invoke`; the host's `new App()` and `Dispatcher.Run()` could invoke `App.OnStartup` and ultimately `FinancialDatabaseStartup.InitializeAsync` against the above ProgramData path. Source references: `WpfTestHost.cs` lines 34–43, `App.xaml.cs` lines 37–60 and 228–234, `FinancialDatabaseStartup.cs` lines 40–108. EF design-time commands instead use `Data Source=:memory:` (`FinancialManagementDesignTimeDbContextFactory.cs` lines 9–16), and the inspected core test fixtures use explicit `%TEMP%`/in-memory databases. Build/restore hooks and environment/config fallbacks into ProgramData were not found.
6. **Business data changed:** Across the retained old snapshot and current main DB copy, **NO**: canonical schema and every row—including all payment, allocation, treasury, user, and migration-history rows—match. This conclusion applies to those two snapshots; it cannot reconstruct hypothetical transient writes/deletes between them. The earlier forensic interval also had no matching timestamped business rows or application audit table. There is no migration 005.
7. **Root-cause fix:** `App` now has a default production constructor and an internal explicit `runProductionStartup: false` resource-only constructor; `OnStartup` returns before path resolution/DI/database work in the latter mode. `WpfTestHost` selects it. Installed/normal `new App()` retains the production path and startup behavior.
8. **Permanent safety guard:** `scripts/verify-programdata-unchanged.ps1` fingerprints existence, length, UTC last-write ticks, and SHA-256 for the main DB, `-wal`, and `-shm`, using filesystem read streams only. It does not load SQLite or open a SQLite connection. It declines production fingerprinting with a controlled failure when the production Desktop/Tresoria process is detected, and fails if files change while individually hashing. `scripts/verify-foundation.cmd` captures before tool restore and verifies on both successful and ordinary failed command paths, reporting each changed property and failing Foundation. An independent outer capture also surrounded the final Foundation run.
9. **Files changed by this task:** `scripts/verify-foundation.cmd`, `src/FinancialManagement.Desktop/App.xaml.cs`, `tests/FinancialManagement.Desktop.Tests/WpfTestHost.cs`; newly untracked `scripts/verify-programdata-unchanged.ps1`, `tests/FinancialManagement.Desktop.Tests/WpfTestHostSafetyTests.cs`, `tests/FinancialManagement.Tests/FoundationDatabaseIsolationTests.cs`, `tests/FinancialManagement.Tests/FoundationProgramDataSafetyGuardTests.cs`, and this report.
